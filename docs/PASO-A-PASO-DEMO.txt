===============================================================================
 SIMULADOR DE MIGRACIÓN - PASO A PASO PARA LA DEMO LOCAL
===============================================================================

Objetivo:
  Presentar el backend funcionando en local, sin depender de Internet,
  sin seguridad remota y con datos demo reproducibles.

Alcance:
  - Todo Docker (backend + PostgreSQL).
  - Sin JWT, sin túnel, sin CORS, sin TLS.
  - Datos demo cargados por Flyway (V1 a V4).

Directorio de trabajo:
  <ruta-del-repo>  (la carpeta con pom.xml, frontend/ y src/)

Datos demo:
  Legajo:               1100001
  Plan actual:          1121 - Tecnicatura Universitaria en Desarrollo de Software
  Plan destino:         1621 - Ingeniería en Informática
  Legajo multi-carrera: 1100002 (1621 Ingeniería + 5010 Contador Público)
  Equivalencias:        Res. 123/21 (3.4.225 -> 3.4.069)
                        Res. 456/22 (3.4.164 -> 1.1.144, entre facultades)

Puertos:
  Backend:  8080
  Postgres: 5433 (host) -> 5432 (contenedor)

===============================================================================
 FASE 0 - PREFLIGHT (5 minutos, hacerlo el día anterior y el día de la demo)
===============================================================================

0.1. Abrir una terminal en el proyecto.

0.2. Verificar que Docker esté corriendo:

     docker info

     Esperado: información del daemon, sin errores.

0.3. Verificar que exista el archivo .env:

     ls -la .env

     Esperado: el archivo existe.
     Si no existe:

     cp .env.example .env

     Y revisar que DB_NAME, DB_USER, DB_PASSWORD y DB_HOST_PORT sean correctos.

0.4. Verificar que los puertos estén libres:

     ss -ltnp | grep -E ':8080|:5433'

     Esperado: sin salida (puertos libres).
     Si hay algo ocupado:
       - Identificar el proceso.
       - O bien detenerlo.
       - O bien cambiar APP_PORT y DB_HOST_PORT en .env.

0.5. Verificar que no haya contenedores viejos del proyecto:

     docker compose ps

0.6. Validar la configuración de Compose:

     docker compose config --quiet

     Esperado: sin errores.

0.7. (Opcional) Backup de la base actual:

     docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-$(date +%F).sql

     Nota: si la demo se hace desde cero, este backup no es necesario.

===============================================================================
 FASE 1 - ENSAYO DE ARRANQUE DESDE CERO (15-20 minutos)
===============================================================================

Objetivo:
  Comprobar que el proyecto funciona sin depender de ningún estado previo.

1.1. Bajar todo y borrar el volumen de la base:

     docker compose down -v

     Esto elimina:
       - Contenedores.
       - Red.
       - Volumen simulador_db_data (todos los datos).

     Esto NO elimina:
       - Imágenes.
       - Archivos del repo.

1.2. Reconstruir la imagen del backend:

     docker compose build --pull

     Tiempo esperado:
       - Primera vez: 2-5 minutos (descarga dependencias de Maven).
       - Veces siguientes: 30-60 segundos.

1.3. Levantar todo:

     docker compose up -d

1.4. Ver el estado:

     docker compose ps

     Esperado:
       - simulador-db: Up (healthy)
       - simulador-backend: Up

     Nota: el backend tiene healthcheck en /actuator/health. El contenedor
     puede figurar "Up" antes de que Spring termine de arrancar, así que
     esperar igual.

1.5. Seguir los logs hasta que arranque:

     docker compose logs -f backend

     Esperado, en orden:
       - Flyway: "Successfully applied 4 migrations"
       - Spring: "Started SimuladorApplication in X seconds"

     Tiempo esperado: ~15-25 segundos después de levantar.
     Cortar con Ctrl+C cuando aparezca "Started SimuladorApplication".

1.6. Verificar salud:

     curl -s http://localhost:8080/actuator/health

     Esperado:
       {"groups":["liveness","readiness"],"status":"UP"}

1.6b. Verificar Swagger (opcional, solo en desarrollo):

      Swagger está deshabilitado por defecto. Para probarlo en desarrollo,
      levantar el backend con:

        SPRINGDOC_API_DOCS_ENABLED=true SPRINGDOC_SWAGGER_UI_ENABLED=true ./mvnw spring-boot:run

      y abrir en el navegador:

        http://localhost:8080/swagger-ui.html

      Esperado: la página de Swagger UI con los endpoints agrupados por
      controller (plan-controller, estudiante-controller, simulacion-controller,
      equivalencia-controller, reporte-controller).

1.7. Verificar que Flyway aplicó las cuatro migraciones:

     docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select version, description, success from flyway_schema_history order by installed_rank;"'

     Esperado:
       V1 | esquema inicial       | t
       V2 | datos demo            | t
       V3 | multi carrera facultades | t
       V4 | planes reales         | t

1.8. Verificar los datos demo:

     docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select legajo, nombre, apellido from estudiante;"'

     Esperado:
       1100001 | Alumno  | De Prueba
       1100002 | Alumna  | Multi Carrera

1.9. Verificar los endpoints principales:

     curl -s -H "X-Legajo: 1100001" "http://localhost:8080/api/v1/planes?excluir=1121"
     curl -s http://localhost:8080/api/v1/planes/1621
     curl -s -H "X-Legajo: 1100001" http://localhost:8080/api/v1/estudiantes/situacion
     curl -s -H "X-Legajo: 1100002" http://localhost:8080/api/v1/estudiantes/situacion
     curl -s -H "X-Legajo: 1100001" http://localhost:8080/api/v1/estudiantes/historial
     curl -s -X POST http://localhost:8080/api/v1/simulaciones -H "X-Legajo: 1100001" -H "Content-Type: application/json" -d '{"codigoPlanOrigen":"1121","codigoPlanDestino":"1621"}'
     curl -s -X POST http://localhost:8080/api/v1/simulaciones -H "X-Legajo: 1100002" -H "Content-Type: application/json" -d '{"codigoPlanOrigen":"1621","codigoPlanDestino":"5010"}'
     curl -s http://localhost:8080/api/v1/equivalencias

     Verificar:
       - Planes: devuelve 1621, 5010, 5015, 5020, 5030 y 5040, con facultad.
       - Plan 1621: 51 materias.
       - Situación 1100001: planesActivos [1121].
       - Situación 1100002: planesActivos [1621, 5010] (multi-carrera).
       - Historial: 8 materias.
       - Simulación 1121 -> 1621: 51 ítems, 3 aprobadas, 5 reconocidas.
       - Simulación 1621 -> 5010: reconocimientos entre facultades (Res. 456/22).
       - Simulación 5010 -> 5015: actualización de plan de la misma carrera.
       - Equivalencias: 2, Res. 456/22 y Res. 123/21.

1.10. Anotar el tiempo total real:

     Desde "docker compose down -v" hasta el primer endpoint OK.
     Ese número define cuánto margen necesitás antes de presentar.

1.11. Anotar cualquier paso manual que hayas tenido que hacer.

     Si hiciste algo a mano (insertar datos, cambiar credenciales, tocar
     el volumen), eso es una dependencia oculta: hay que llevarlo al repo
     o al .env, o la demo no es reproducible.

===============================================================================
 FASE 2 - PREBUILD ANTES DE PRESENTAR (el día anterior)
===============================================================================

Objetivo:
  Que el día de la demo no haya que compilar ni descargar nada.

2.1. Construir la imagen:

     docker compose build --pull

2.2. Descargar la imagen de PostgreSQL:

     docker compose pull db

2.3. Verificar que las imágenes estén locales:

     docker images | grep -E 'simulador|postgres'

2.4. NO hacer "down -v" después del prebuild para conservar la base.
     Para demo desde cero, hacerlo antes del prebuild, no después.

2.5. El día de la demo, levantar sin build:

     docker compose up -d

     Nunca usar --build en vivo salvo que hayas cambiado código.

 PASO 8 - Simulación (90 segundos, el corazón de la demo)
------------------------------------------------------------------------------

   curl -s -X POST http://localhost:8080/api/v1/simulaciones \
     -H "X-Legajo: 1100001" \
     -H "Content-Type: application/json" \
     -d '{"codigoPlanOrigen":"1121","codigoPlanDestino":"1621"}'

   Mostrar y explicar:
     - 51 ítems (plan real de Ingeniería).
     - 3.4.069 reconocida por equivalencia Res. 123/21 desde 3.4.225.
     - 3.4.164 y 3.4.072 reconocidas como misma materia.
     - 3.4.075 queda FINAL y 3.4.207 CURSANDO.
     - Resumen: 3 aprobadas, 1 final, 47 pendientes de cursado,
       5 reconocidas, 14 pendientes del plan actual, 48 del plan nuevo.
     - Título intermedio: 3 de 31, 10 %.
     - Optativa sin correspondencia: OPT-TDS-I.

   Cambio de facultad (multi-carrera, opcional):

   curl -s -X POST http://localhost:8080/api/v1/simulaciones \
     -H "X-Legajo: 1100002" \
     -H "Content-Type: application/json" \
     -d '{"codigoPlanOrigen":"1621","codigoPlanDestino":"5010"}'

   Mostrar:
     - Origen Ingeniería (1621) -> destino Contador Público (5010).
     - 1.1.144 reconocida por equivalencia Res. 456/22 desde 3.4.164.
     - 1.1.083, 1.3.067 y 1.3.068 reconocidas como misma materia.

   Actualización de plan de la misma carrera (opcional):

   curl -s -X POST http://localhost:8080/api/v1/simulaciones \
     -H "X-Legajo: 1100002" \
     -H "Content-Type: application/json" \
     -d '{"codigoPlanOrigen":"5010","codigoPlanDestino":"5015"}'

   Mostrar:
     - Contador Público plan 2022 (5010) -> plan 2026 (5015).
     - Las materias compartidas se reconocen como misma materia; la nueva
       (1.3.077 Contabilidad y Nuevas Tecnologías) queda A_CURSAR.

 FASE 4 - PLAN B
===============================================================================

B.1. Si Docker no arranca:
     - Verificar "docker info".
     - Reiniciar Docker.
     - Último recurso: backend local con JDK 21 y DB en Docker.

B.2. Si el puerto está ocupado:
     - Cambiar APP_PORT y DB_HOST_PORT en .env.
     - "docker compose up -d" (no hace falta rebuild por puerto).
     - Actualizar la URL en api.http y en el navegador.

B.3. Si faltan datos:
     - "docker compose down -v".
     - "docker compose up -d".
     - Esperar "Started SimuladorApplication".

B.4. Si el backend no toma cambios de código:
     - "docker compose up -d --build backend".

B.5. Si algo falla en vivo:
     - No debuggear frente a la audiencia.
     - Pasar a capturas de pantalla o video grabado.
     - Seguir con el guion oral.
